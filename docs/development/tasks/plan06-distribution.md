利用者指定の公開リポジトリは [shijun537/pi-gui-ja-base](https://github.com/shijun537/pi-gui-ja-base)。追加の公開先を作らず、このリポジトリに識別子を結び付ける案を推奨する。以下は採用前の提案であり、今回ビルドした設定ではない。

| 表示名                                 | `Pi-GUI JA Base`                                           | 公開ソース名と対応し、上流版や一般名の独立フォークと区別できる。非公式フォークの説明は保持する     |
| appId / AppUserModelID                 | `io.github.shijun537.pi-gui-ja-base`                       | 指定リポジトリの名前空間を使う。初回バイナリ公開前に固定し、その後は安易に変更しない               |

従来の専用コピーは `Pi-GUI Independent`、`com.pi-gui.independent.desktop`、`pi-gui-independent.exe`、`%APPDATA%\pi-gui-independent\agent` を使っている。その結果は上の新候補を検証したことにはならない。新名称を採用する場合は同じ範囲を再ビルド・再検証する。単に表示名だけを変えて既存結果を流用しない。

従来候補には、独立版起動時に `PI_CODING_AGENT_DIR` を無条件でアプリ配下へ上書きする処理がある。これは静的に確認した事実で、今回の起動試験で確認できた挙動ではない。この問題に対する修正候補は次のとおり作成した。

## 明示された保存先を尊重する追加パッチ

専用のソースコピーで、保存先の解決を `resolveIndependentWindowsDataPaths` へ抽出した。独立 Windows 版の起動処理はアプリ用と Pi 用の環境変数をこの関数へ渡し、Pi 用が明示されていればその値を保持する。空欄・空白だけの指定は未指定として扱い、前後の空白は除く。非独立版の既存の解決処理は維持する。

| 指定条件       | アプリ保存先           | Pi 保存先            |
| -------------- | ---------------------- | -------------------- |
| どちらも未指定 | 独立版の既定保存先     | その配下の `agent`   |
| アプリだけ明示 | 明示されたアプリ保存先 | その配下の `agent`   |
| Pi だけ明示    | 独立版の既定保存先     | 明示された Pi 保存先 |
| 両方を明示     | 明示されたアプリ保存先 | 明示された Pi 保存先 |

修正は従来の `Pi-GUI Independent` 候補へ追加する2ファイルの小さなパッチとして保存した。従来候補自体と共有アプリには適用していない。推奨する新名称へ切り替えた実装・バイナリを作成したわけでもない。

Node 24.22.1 で、テスト側の再実装ではなく実際の抽出関数を読み込み、合成 Windows パスによる上の4条件、空欄、前後の空白とパス中の空白を検証した。入力オブジェクトが変更されないことと、専用コピーの起動処理が両方の指定を関数へ渡すことも確認し、計7件が成功した。抽出関数の strict 型検査と、従来候補を対象とする追加パッチの `git apply --check` も終了コード0だった。

この追加検証では GUI を再起動していない。修正後の実 Electron、既定保存先への実際の書き込み、上流同居、パッケージ済み成果物は未確認であり、製品採用時には必要な検査と合わせて確認する。

## Windows と署名の扱い

対応候補は Windows x64 に絞る。過去の独立候補の記録は OS ビルド26300、Electron 37.10.3、版番号1.0.1によるもの。これは Windows の最低対応版、全 Windows 11 への対応、音声入力の最低 RAM・GPU・空き容量を証明しない。採用 Electron と音声構成を固定して対象端末で計測するまでは、検証した構成のみを記載する。

署名方式は未確定。今回の既存候補は未署名で、証明書の発行者名・Subject・有効期限は存在するものとして記載しない。署名サービスの契約、証明書発行、新しい認証情報の作成は行っていない。候補の比較は [計画02の署名候補](../windows-update.md#署名の候補)を参照し、契約の実行や利用資格の確認済みという扱いにしない。

正式な更新を採用する場合は、署名後のセットアップと `latest.yml` のファイル名・サイズ・SHA-512、実際の証明書から得た発行元、タイムスタンプと Windows の信頼検証をそろえる。発行元を推測した文字列で設定しない。未署名の非公開更新成功を公開版の署名付き更新の証明にしない。署名未確定のまま正式配布済みとは案内しない。

## LP・ヘルプに載せる時点

日本語紹介5ページ、利用案内、Pi 導入と合成データを使った実アプリ画面2枚は既存の公開ソースに含まれる。Pagesの有効化と親担当によるbuild/deploy成功、[公開URL](https://shijun537.github.io/pi-gui-ja-base/)の発行を確認した。公開後のHTTP確認とブラウザー実表示は同担当で別に確認する。過去の `deploy: skipped` を現在の未設定の証明として扱わない。最新の結果は [サイト公開記録](../website-publication-plan.md)を正本にする。

サイト配信と Windows ダウンロードの公開は別の成果である。配布物が未公開の間はソースの導入を案内し、上流のバイナリを本フォークのダウンロードとしてリンクしない。配布時は次をそろえる。

1. 同じ採用構成の候補で、計画02・05の必要な検証と [共通検査](../../ci-baseline.md)を完了する。
2. MIT と同梱依存の通知を維持し、[ライセンス](../../legal/licenses.md)、[プライバシー](../../legal/privacy.md)、[利用案内](../../legal/terms.md)を実装に合わせる。独立プロファイル化を暗号化・OS 隔離の完成とは説明しない。
3. LP とヘルプの文面に、セットアップ・ポータブルの差、保存先、アンインストール後の扱い、検証した Windows、署名の状態、更新機能の採否を反映する。
4. 公開対象のソース・成果物・案内をそろえる。バイナリの公開は今回実施しておらず、実際に公開する指示と条件を確認した時点で実行する。
5. 公開後、タグを指定してアセットを取得し、保管した検証済みファイルの一覧・サイズ・SHA-256と照合する。更新対応版では署名後のメタデータと blockmap も含める。
