# 計画02：Windows 更新の担当記録

2026-11-26。ソースは [pi-gui-ja-base](https://github.com/shijun537/pi-gui-ja-base) に公開済み。正式な Windows 配布と公開版の更新機能は未完了。[更新方針](../windows-update.md)・[配布計画](../windows-release-plan.md)に対する追加調査と再開条件を記録する。

## 結論と今回の範囲

既存の非公開 1.0.1 → 1.0.2 試験は再利用する。更新を採用した公開版については、署名済み配布候補と製品組み込みの確認が残る。今回、既存ライブラリと終了処理を独立した合成試験で調べ、公開方針のままでは標準ライブラリだけに任せられない箇所を実行確認した。共有アプリ、配布設定、Pi 本体とその版、普段の共有設定、実認証、利用者の会話は変更していない。

今回の完了条件は、既存方針との差を再現し、専用領域に候補と検証を残し、02・06の依存と次の検証を具体化すること。製品更新の完了、正しい署名の受け入れ、置換中断からの復旧完了を意味しない。

## 確定済みの利用者操作

- 新版の検知だけでは取得しない。ダウンロードと「再起動して適用」は利用者が個別に選ぶ。
- 会話が処理中の場合は適用を保留する。下書きと会話の保存が成功するまで終了しない。保存失敗や時間切れでは開いたまま再試行できるようにする。
- セットアップ版とポータブル版を区別し、ポータブル版は手動差し替えとする。
- 更新物の版、対象アーキテクチャ、SHA-512、Windows が信頼するタイムスタンプ付き Authenticode 署名、インストール済み側に設定した発行元を照合する。発行元の設定欠落も拒否する。

## 実行・ソース確認した差と候補

| 対象                 | 確認した挙動                                                                                                                                          | 製品へ移す際の必要条件                                                                                                                       |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 発行元設定           | `NsisUpdater.verifySignature` は `publisherName` がない場合、または `app-update.yml` の読み取りが `ENOENT` の場合、署名検証関数を呼ばず `null` を返す | 製品側で設定欠落を拒否する。初回セットアップ側の設定と更新側の期待値をそろえ、設定欠落試験を残す                                             |
| タイムスタンプ       | 実 verifier は、合成の `Status: 0` と一致する発行元 DN を返すレポートなら `TimeStamperCertificate: null` でも通した                                   | 信頼できる Windows の検証結果に加えて、要求するタイムスタンプ条件を明示する。実際の採用発行元で正の試験を行う                                |
| ダウンロード後の改変 | `DownloadedUpdateHelper.validateDownloadedPath` は同一インスタンスの既検証ファイルについて存在だけを再確認した。合成ファイルの改変を受け入れた        | 起動直前に SHA-512 と署名・発行元を再確認する。検証から実行までの差し替えを許さない保管場所・権限・実行方式も設計する                        |
| 下書き保存確認       | 現行 `PendingComposerDraftFlusher` は、応答期限超過、破棄・クラッシュしたレンダラーを成功と同じ resolve で扱う                                        | 更新用の保存経路は成功・失敗・時間切れを区別する。レンダラーは保存完了後に成功を返し、失敗時は終了しない                                     |
| 既存終了処理         | ソース確認：`electron/main.ts` の `before-quit` は保存失敗を捕捉し、期限超過時も終了する                                                              | 更新開始前に別の保存確認を完了する。更新用の失敗を一般終了の「期限後も終了する」処理へ流さない                                               |
| 試作の適用ロック     | ソース確認：既存 `pilot.mjs` は `quitAndInstall` を遅延実行し、`finally` で先に `applying` を戻す                                                     | 保存開始からインストーラーへの引き渡し、その後の終了までロックを保つ。新規会話、後続送信、承認待ち、スケジュール等の流入も同じ判定に接続する |

ライブラリの調査対象は、既存の非公開試験が使った6.8.12である。製品が同じライブラリを組み込んでいるという意味ではない。採用版が変わった場合は同じ検証を再実行する。

候補 `update-barrier.cjs` は、利用中判定 → 新規作業の受付停止・入力固定 → 全ウィンドウの保存成功 → main の永続化成功 → 利用中の再確認 → 取得物の再検証 → 試行記録の保存 → インストーラーへの引き渡し、の順に進める。どの段階でも失敗すれば解除して戻り、正常な引き渡し後はロックを保持する。10条件で保存失敗、期限超過、レンダラー不在、永続化失敗、取得物変更、試行記録失敗、起動失敗、処理中、競合、正常引き渡しを確認した。正常引き渡しは更新成功ではない。

候補 `signature-policy.cjs` は、ネイティブ検証結果の上で発行元 DN・対象パス・タイムスタンプ情報の存在を判定するだけで、署名検証器ではない。署名チェーン、失効、タイムスタンプの暗号学的な正当性を合成レポートから証明していない。テストの架空 DN は採用発行元ではなく、製品へコピーしてはならない。

独立 Electron の候補も、合成データ専用画面とインストーラーのスタブである。製品 UI、既存 IPC、会話の実行制御への統合は残る。製品へのコピー・採用はしていない。

インストーラー起動後は、終了コード0やハンドオフイベントだけで成功にしない。更新試行の目標版・取得物の識別情報を専用のアプリ管理領域に保存し、次の実プロセスの版と照合する。旧版が開けた場合は失敗として明示的に再試行する。アプリが起動不能ならアプリ内の再試行ボタンは使えないため、検証済みセットアップによる修復・再導入の経路と案内を用意する。自動ロールバックができるという保証はしていない。

置換中断の独立試験では、専用コピーの NSIS テンプレートにチェックポイントを入れ、元テンプレートと配布対象を変更しない。現行テンプレートの `installSection.nsh` は旧版アンインストールの後に `installApplicationFiles` を実行するため、`customInit` で拒否する既存試験だけでは旧版除去後の結果を確認できない。OS の電源断を模した試験と、プロセスだけを止める試験は区別する。今回はどちらも新たに実行できていない。
