## 実装の優先度

1. **既存 UI の日本語化。** サイドバー・起動直後の画面、会話・入力欄、レビュー・右ペイン、Windows 側のアプリ文言を順に進める。現行の操作を日本語で確認してから新機能に進む。 [日本語化の確認条件](#既存-ui-の日本語化)
2. **フォルダ不要のチャット。** Windows の実アプリで、フォルダ未登録から送信し、再起動後に履歴から再開できるところまで確認する。作業フォルダの読み書きとコマンド実行は、合意済みの仕様に沿ってプロジェクト側で有効にする。
3. **「プロジェクトで続ける」。** フォルダを選択し、相談の要点と作業依頼を下書きで確認・編集して送信する。元の会話と新しいプロジェクトの両方に戻れることを確認する。新しい文言は各機能の実装時に翻訳する。 [合意済みの仕様](../chat-project-spec.md)
4. **Windows の配布準備。** 先に [追加9項目の実装ループ](pre-release-feature-loops.md) を進める。その後、セットアップのショートカット選択を実装し、配布物で確認する。実キーを扱う公開構成では、キー保護と、採用した承認・隔離機能を実行経路で確認する。依存の採否は保守手順で判断する。 [保守手順](dependency-maintenance.md)

### 文字だけの主要ボタンの中央揃え

- 「新しい会話」「作成」「最初のフォルダを開く」のように文字だけを表示する主要ボタンは、ボタンの左右と上下それぞれの中央軸に、見えている文字の中心を揃える。折り返す場合も各行を中央揃えにする。
- 新規実装では共通の `.button.button--primary` と、文字を包む `.button__label` を使う。表示言語やフォントによるわずかなずれは共通スタイルで補正する。Windows の実 Electron で対象の言語を表示し、ボタンの外枠と文字を見比べて確認する。

### セットアップのショートカット

- セットアップで「デスクトップにショートカットを作成する」を選べるようにする。既定では選択されておらず、利用者が選んだ場合だけ作成する。スタートメニューからはどちらの場合も起動できる。
- 現行はワンクリックセットアップ。選択肢を表示する実装方式は、セットアップの回で確認する。無人インストールの既定もデスクトップには作成しない。
- 同じ Windows 環境で、未選択と選択済みをそれぞれ試す。日本語のセットアップ画面で選択肢を確認し、インストール、起動、保護設定を維持したアンインストール、試験用の登録と作成したショートカットの片付けを検証する。 [既存の実機検証](progress.md#windows-配布ビルドの再検証)

### Pi-GUI 01｜音声入力の高速化

- **仕様**　音声入力の計画。現行の端末内文字起こしを、録音停止から下書きへの追記まで計測する。約7秒の1本で、自動判定41秒、日本語指定31秒、turbo の日本語指定21秒だった。既存の日本語音声に数字や技術用語を含む素材を加え、large-v3 の日本語指定と GPU 実行を比較する。言語選択、必要なら turbo、GPU が使えない場合の動作を検討する。
- **完了条件**　同じ素材で待ち時間・誤認識・必要メモリを記録し、配布候補でオフラインと下書き保持を確認する。実マイクで聞き取りと待ち時間を確認する。
- **判断点**　モデル変更や最低動作スペックは計測後に判断する。
- **担当案**　Sol・Medium が実装と計測。Astra・High が GPU の動作根拠、品質比較、CPU に戻る条件を調査。

### Pi-GUI 02｜Windows アプリの更新

- **仕様**　更新の確認、ダウンロード、再起動して適用する流れを設計する。セットアップ版とポータブル版の扱い、配布先・更新先、署名と取得物の検証方法を比較する。独立版としての更新先は計画06と共有する。
- **完了条件**　非公開の旧版・新版で検知、適用、中断・失敗、再試行、会話と設定の保持を検証する。
- **判断点**　更新先、署名方式、適用時期、ポータブル版の対象範囲を決めてから実装する。
- **担当案**　Astra・High が更新の信頼性とデータ保持を設計・レビュー。Sol・Medium が試作と旧版からの検証。 [公開版の方針と非公開試験](windows-update.md)

### Pi-GUI 03｜API キー保護と Windows の隔離

- **仕様**　キーの保存・復号・送信先を洗い出し、暗号化と送信先検証を設計する。MXC はオプションの検証候補として、承認機能との役割分担と Windows での対応範囲を確認する。
- **完了条件**　ダミーキーで意図した宛先への認証、別宛先への転送の防止を確認する。MXC を試す場合は、配布候補でエージェントと子プロセスのアクセス制限と許可済み API の動作を確認する。
- **判断点**　MXC の採否と、実キーを扱う公開構成の条件を判断する。
- **担当案**　Astra・High が保存・復号・送信と隔離の設計をレビュー。Sol・Medium が合成データで実装・検証。
- **最初の区切り**　Sol・Medium がコードから保存・復号・送信と既存設定の互換性を整理し、ダミーキーで確かめる順番を開発進捗に残す。資料をもとに Astra・High が設計をレビューしてから、端末内のテスト先で登録済み宛先への認証と別宛先へのキー転送防止を確認する。MXC はその結果を踏まえて採否を判断する。

### Pi-GUI 04｜Electron 更新候補と依存関係

- **仕様**　検証済み Electron 候補の記録を確認し、採用時点のサポート状況と既存差分との互換性を調べる。Pi・Electron を別の差分で扱い、Dependabot の npm 監視案も切り分ける。
- **完了条件**　採用候補でセットアップ・ポータブル起動・日本語・内蔵端末・同梱依存を確認し、計画05へ候補構成を渡す。
- **判断点**　Electron の取り込み可否を判断する。Pi の版変更は事前に確認する。Jev は保留中。
- **担当案**　Sol・Medium が互換性と実機検証。Astra・High が更新差分とネイティブ依存への影響をレビュー。

### Pi-GUI 05｜Windows セットアップと配布候補の検証

- **仕様**　デスクトップショートカットを希望者だけ作成する選択欄を日本語で実装する。無人インストールも既定オフとし、スタートメニューからはどちらの場合も起動できるようにする。計画01〜04の採否を反映して最終候補を構成する。
- **完了条件**　選択あり・なしのインストール、起動、再起動、アンインストール、ポータブル起動、採用機能を同じ配布候補で検証する。同梱物の検査と混入確認も行う。
- **判断点**　初回に含める機能、対応 Windows、署名の方針を確定する。
- **担当案**　Sol・Medium がセットアップと配布テスト。Terra・Medium が日本語画面と Windows 実機操作を確認。

### Pi-GUI 06｜独立配布と LP・ヘルプの案内

- **仕様**　独立版の配布・更新先、アプリ名・識別子、Windows 向け公開経路、ライセンス表示を整理する。更新先の設計は計画02と連携する。配布候補の検証が済んだ段階で、LP とヘルプの配布リンクを一緒に検討する。 [計画02との共有方針](windows-update.md#公開版の方針)
- **完了条件**　対応環境、インストール方法、変更点、署名状態を案内に反映する。公開承認後に、取得できる成果物と検証済み候補の一致を確認する。
- **判断点**　配布候補・公開先・案内の確認後に公開承認を求める。配布リンクと LP は候補が整うまで保留する。
- **担当案**　Sol・Medium が配布設定と案内。Astra・High が上流との識別と公開経路をレビュー。Terra・Medium が LP とヘルプの導線を確認。

## 同じ配布候補で検証をまとめる

公開候補のセットアップ版とポータブル版を一度生成し、同梱依存の確認、実機での起動と対象機能、配布物の混入検査に同じ成果物を使う。セットアップ版ではインストールと再起動、ショートカットの両条件、アンインストールを確認し、ポータブル版の起動も確認する。同じ成果物で配布時の起動性能まで測る場合は、その計測条件と結果を評価記録から参照する。 [Windows 配布診断](../../.github/workflows/windows-release-diagnostic.yml) · [評価手順](evaluation.md)

保守時の実機結果は、セットアップ版とポータブル版のハッシュ、対象機能、Windows 環境、確認条件が配布記録と一致する場合に使う。残りの項目は配布前に実施する。セットアップ設定や同梱ファイルが変わった場合は、新しい候補で影響する確認をやり直す。公開時は実際に取得できるファイルと検証済みの成果物の一致を確認する。
