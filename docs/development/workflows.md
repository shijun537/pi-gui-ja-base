# 開発・検品の進め方

[開発進捗](progress.md) で着手範囲を確認し、変更の種類に合った手順を選ぶ。共通の作業規則は [AGENTS.md](../../AGENTS.md) と、この文書の「作業全般の基準」を参照する。

## ループ設計の基準

- **一つの目的で閉じる。** 実装は承認された仕様の実現、保守は依存候補の互換性と採否を扱う。開始条件、変更範囲、完了条件、記録先を決めてから回す。
- **範囲が変わったら課題を渡す。** 保守で現行仕様を保つための互換修正は、更新候補の範囲に含められる。製品仕様の変更が必要なら候補を保留し、実装側に課題を記録する。実装中に依存の選定や更新が必要になった場合は、保守側に分けて記録する。
- **評価は単独で実行する。** [評価手順](evaluation.md) で性能・推論品質を測り、条件と結果を残す。実装・保守では、対象の版と条件が一致する評価結果を必要なときに参照する。

## 共通の流れ

1. **範囲を決める。** 依頼、成功条件、実際の作業ツリーを照合する。既存差分が混在している場合は、何を採否の対象にするか記録する。
2. **範囲に合う検査を選ぶ。** 共通検査は [CI 基準](../ci-baseline.md)、デスクトップの確認範囲は [テスト規則](../../apps/desktop/tests/AGENTS.md) に従う。
3. **既存の結果を照合する。** 対象差分と、その確認に影響する依存の版・環境・実行条件が一致する結果は、次のループでも参照する。配布物の確認では成果物が同一であることも照合する。差分や条件が変わった確認、結果が不明な確認は実施する。単体、実 Electron、実プロバイダ、配布物の検証は、実際に確認した範囲を記録する。
4. **判断と残件を一か所に残す。** 採否、未実施・失敗の理由、次に確認することは、下の表の記録先に書く。別のループや [開発進捗](progress.md) からは、その記録を参照する。

| ------------------------------------ | ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| GUI の機能実装                       | 合意済みの仕様から開始し、対象の成功条件を確認して実装結果を記録する。 | [実装ループ](#実装ループ) · [Windows 実機手順](../../.agents/skills/testing-windows-desktop/SKILL.md)。実プロバイダで確認する場合は [専用手順](../../.agents/skills/verify-pi-gui/SKILL.md) を使う。 |
| Pi・Electron・採用後の MXC の更新    | 更新候補から開始し、既存機能の互換性を確認して採用・保留を記録する。   | [依存関係の保守](dependency-maintenance.md)。結果は更新記録または PR に残す。                                                                                                                        |
| 性能・推論品質の評価                 | 計測対象と比較条件から開始し、測定値と未確認項目を記録する。           | [評価手順](evaluation.md)。現行版だけの基準計測にも使える。                                                                                                                                          |

実装で確認した既存機能のテストは、影響を受ける依存の更新時に再利用できる。たとえば「プロジェクトで続ける」の動作テストは、実装後の Pi 更新でも使う。

検品済みの差分は、対象と基準を照合して既存の採否を参照する。再検品が必要な場合は、`pnpm check` に含まれる検査を個別に繰り返さず、変更された箇所と以前の検証で確認できていない条件を対象にする。 [検品手順](../../.agents/skills/review-pi-gui-fork-work/SKILL.md#verify-do-not-assume)

Jev を評価に採用した場合は、Windows の配布前に [Jev の API キー運用](evaluation.md#jev-の-api-キー運用) の配布物確認を行う。

## 実装ループ

1. **一つ選び、対象の動作環境を先に通す。** [実装の優先度](windows-release-plan.md#実装の優先度) から今回の利用者操作と成功条件を決め、`git status --short` で混在差分を特定する。デスクトップの変更は、最小の既存テストで Windows の実 Electron が専用プロファイルで起動することを確認する。画面文言を照合するテストは言語を明示する。セットアップや更新が対象なら、手元で配布候補を生成・起動できるかも先に確認する。同じ条件での成功記録があれば使う。
2. **担当を選び、必要なサブエージェントを実行する。** 保存・実行権限・外部送信・OS 連携などが成功条件に関わる場合は、画面全体を作る前に実行経路をたどる。対象の入口と、実行・保存・通信が実際に起きる箇所を照合し、拒否やキャンセル時に何が起きるかを確認する。必要に応じて下記の役割分担で、実装前の時点で具体的な論点を委任する。途中で実行経路が変わった場合は、影響した論点を再確認する。
3. **最小の利用者操作を実装する。** 入力から実行結果まで一つ通してから、画面や設定の範囲を広げる。送信のテストは、ローカルの合成モデルで実際の会話要求を確認する。タイトル生成など別の要求と区別し、再開のテストデータは、既存の方法で動作実績のある履歴かアプリで生成した履歴を使う。保存項目を変える場合は、既存データを開いた状態で一度保存し、同じプロファイルで再起動する。画面文言は既存の翻訳カタログで管理する。 [翻訳の規則](../../apps/desktop/src/i18n/AGENTS.md)
4. **対象の検査から広げる。** 変更した操作を対象のテストで確かめる。失敗時は最初のエラーや記録から、実装、テストデータ・画面の探し方、起動・権限・終了待ちなどの環境のどこで止まったかを特定し、原因を直した確認だけを先に再実行する。既存テストが示した動作は再利用する。OS のダイアログや周辺機器は実機、セットアップと更新は対象の配布物で確認し、画面や合成データで確認した結果と合わせて記録する。関連変更がそろった最終状態で `pnpm check` を実行する。 [実行方法と検証範囲](../../apps/desktop/README.md)
5. **結果を残して次へ進む。** [開発進捗](progress.md) に実行環境、確認できた操作、残件を記録する。やり直した場合は原因と次回に前倒しできる確認を、既存の結果欄に残す。サブエージェントを使った場合は論点と結果の反映先も残す。依存の採否は [保守手順](dependency-maintenance.md)、性能や品質の測定は [評価手順](evaluation.md) に渡す。

**実装の単位。** 単独で動作を確認できる仕様は、一つずつ実装・検証してから次へ進む。同じ利用者操作を成立させる変更や、途中の状態では成功条件を確認できない変更は、一回の実装にまとめる。たとえば、起動直後の画面とサイドバーの文言は、フォルダ未登録・登録済みを確認する一回の日本語化として扱う。フォルダ不要のチャットは、履歴からの再開まで確認した後に「プロジェクトで続ける」へ進む。

**モデルとサブエージェント。** 既存 UI の日本語化と軽い修正は、実装を担当するチャットで差分と動作を確認して進める。フォルダ不要のチャットの保存・再開や「プロジェクトで続ける」の引き継ぎなど、データ消失や誤った保存先につながり得る論点がある場合に、対象を絞ってサブエージェントへ読み取り調査・レビューを依頼する。再確認は指摘した論点に絞る。依頼元が編集と最終確認を担当する。Codex でのモデルの目安は、本作業が GPT-6.2 Sol・Medium、サブエージェントが GPT-6.2 Astra・High。Claude Code でも同じ役割分担を使える。 [Claude Code での再開手順](claude-handoff.md)

Windows で `test:e2e:runner` が `sh` を見つけられない場合は、`pnpm --dir apps/desktop run build` を先に実行し、ルートで `pnpm exec playwright test -c apps/desktop/playwright.config.ts <対象のテストファイル>` を実行する。Core の確認は `PI_APP_TEST_LANE=core`、`PI_APP_REAL_AUTH=0` を設定し、専用プロファイルを使う。

## 作業全般の基準

1. 実際に少なくとも1回は正常に実行されることを確認してください。シミュレーション環境でのテストは対象外です。
2. 最もシンプルなバージョンから始めてください。コード行数が300行を超えると予想される場合は、その理由を事前に説明する必要があります。
3. 追加レビューが必要な場合は最大2回とします。それ以降は、「コードが最後まで実行されない」または「データが破損する」という問題のみがブロック対象となります。
4. 時折の繰り返しや手動での修正が必要になることは許容されます。完璧さを追求するわけではありません。
5. 元に戻せる変更については承認は不要です。データの削除、資金の関与、公開につながる変更、または権限の変更のみが承認の対象となります。
6. 新しいルールやレビュー段階を追加する場合は、私の承認を得る必要があり、同時に既存のルールを削除できるかどうかも説明してください。
7. 同じ問題で2回行き詰まった場合は、作業を中断し、3つの簡単な文を使って平易な言葉で私に尋ねてください。問題を回避するための新たな回避策を導入しないでください。
8. 報告の際は、自分が何を行ったか、結果をどのように個人的に検証したか、そして次のステップは何かについてのみ記述してください。ハッシュ値や専門用語は含めないでください。
