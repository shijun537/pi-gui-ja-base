# ④ Windows 配布準備の前に進める追加機能

9項目の実装順と完了条件。着手順は A → B → C → D → E → F。A〜C は既存の機能・テストを先に確認し、足りない箇所だけを修正する。D〜F は各項目の実行経路を先に確認し、必要な利用者判断を反映する。初回配布に含める範囲は、該当ループの完了条件を満たしたことを確認して④へ渡す。 [9項目の仕様案](windows-release-plan.md#追加機能の仕様案)

## 実装ループ

各ループの着手時に、[共通の実装ループ](workflows.md#実装ループ) に沿って担当モデルとサブエージェントの要否を決める。通常の実装・検証は Sol・Medium が担当する。履歴や設定の保持、承認が適用される実行経路、音声の送信先などに具体的な論点がある場合は、Astra・High を起動し、対象を絞った読み取り調査・レビューを依頼する。主担当が結果を確認し、実装や完了判断に反映する。

## 着手前に必要な判断

- **D 段階的な承認**は、Pi 標準ツールを対象にする。既存プロジェクトは「従来の設定」で継続し、制限モードを明示的に選ぶと、そのプロジェクトの会話では拡張・MCP を停止する。手動ターミナルは利用者自身が操作する。Pi の版変更が必要な場合は先に確認する。
- **F 更新**は、更新の配布先、ダウンロード・適用のタイミング、署名・検証方法、ポータブル版の扱いを決める。自動更新を先に確認する場合は、④より前に検証用インストーラーを作る作業を含む。

## D の入力欄の表示と適用範囲

プロジェクトの会話では、入力欄の下で添付ボタンの右に、現在の権限を示すプルダウンを置く。閉じているときはアイコン、短いラベル、下向きの矢印を表示する。開くと各選択肢の説明と、現在の選択が分かるチェックを表示する。

| アイコン | ラベル       | 選択肢の説明                                                               |
| -------- | ------------ | -------------------------------------------------------------------------- |
| 盾       | 読むだけ     | プロジェクトのファイルを読めます。編集やコマンドの実行はできません。       |
| 手       | 確認して作業 | ファイルを編集したり、コマンドを実行したりする前に、操作ごとに確認します。 |
|          | 従来の設定   | プロジェクトに設定済みのツールや拡張・MCP を使います。                     |

変更はプロジェクト単位で保存し、アプリの再起動後に適用する。それまでは現在のモードと適用予定を表示する。再起動を境界にして、既に読み込まれた拡張やランタイムを制限付きの会話に引き継がない。制限が及ぶのは対象プロジェクトの Pi ツール。別のプロジェクトで有効な拡張は引き続き動作する。承認したシェルと子プロセスの OS レベルの隔離は Windows の MXC 試験で扱う。

## 工数の抑え方

既存の会話リンクは行番号を伴うファイルリンクに対応している。B の最初に、行番号なしの `.md` リンクとファイル単位の外部エディター起動を照合する。既存のネイティブメニューは macOS 向けなので、C では Windows の入口を追加する。現行の定期更新確認は上流リポジトリを参照しているため、独立版での案内と定期確認の扱いは同じ判断で決める。 [会話のリンク処理](../../apps/desktop/src/features/conversation/workspace-file-line.ts) · [既存の更新確認](../../apps/desktop/electron/platform/update-checker.ts)

- A〜C は既存の Windows 実 Electron テストを使い、同じビルドで確認できる操作はまとめる。仕様をすでに満たす項目は変更せず、確認結果を [開発進捗](progress.md) に記録する。ピン留めとフォルダ色は、同じビルドを使える場合に再起動を共用する。日本語の表示を重点的に確認し、英語は影響した主要操作を同じテストで確認する。関連する差分で全体検査をまとめる。 [実装ループ](workflows.md#実装ループ)
- D〜F は実装前の調査で、次の判断に必要な操作を一つ通す。E は [端末内での文字起こし](#e-端末内での文字起こし) の初回計測から始める。F は採用した更新方式について、画面を作る前に非公開の旧版・新版を使い、更新が届く経路と適用に失敗した場合の挙動を確かめる。結果を見て、追加依存と配布構成の変更範囲を決める。
- 一時クローンは C のメニュー、E のローカル文字起こし、F と④の Windows 更新・セットアップで必要な箇所を参照する。参照が終わったクローンは削除する。採用しない方式のクローンも削除する。electron-builder は F と④の両方で使う場合、最後の参照の後に削除する。 一時参照リポジトリの一覧（ローカル試験資料・公開対象外）

## E 端末内での文字起こし

端末内処理を採用し、音声を外部に送信しない。OpenAI Whisper の標準 `large-v3` を日本語の品質基準にする。計測には量子化していないモデルを使い、同じモデルと音声で性能を比較する。 [OpenAI のモデルカード](https://huggingface.co/openai/whisper-large-v3) · [whisper.cpp のモデルとメモリの資料](https://github.com/ggml-org/whisper.cpp#memory-usage)

1. **計測条件を固定する。** Windows x64 で `whisper.cpp` の版を固定し、公式配布先の非量子化 `large-v3` と `large-v3-turbo` を照合する。端末内で生成した短い日本語音声を、日常文と英数字・技術用語を含む文で用意する。各モデルで同じ音声、言語、実行条件を使う。
2. **品質と待ち時間を測る。** 参照文との文字誤り、モデルサイズ、読み込みを含む待ち時間、最大メモリ使用量を記録する。CPU で実行した結果を先に取り、GPU を実際に利用できる構成があれば同条件のモデル比較を行う。比較用の合成音声の結果と、実マイクの聞き取りやすさはそれぞれ記録する。最低動作スペックは候補構成での実測後に決める。
3. **モデルを初回利用時に取得する。** 利用者確認済み。Windows x64 のアプリには CPU 用の実行部を同梱する。初回のマイク操作で約3.1 GBと表示し、利用者が選んだ場合に `large-v3` を取得する。取得後はオフラインで文字起こしできる。
4. **録音から下書きまで一つ通す。** 既存の入力欄の共通部品を使い、利用者が押したときに録音する。アプリ自身の画面だけに音声の録音を許可し、最大30秒の音声をメモリからローカル処理へ渡す。録音停止後の結果は編集可能な下書きとして追記する。既存の下書きを保ち、会話を切り替えた後に古い結果を挿入しない。送信は利用者が操作する。録音中のキャンセル、モデル未取得、ダウンロード失敗からの再試行を検証する。
5. **Windows 実機で確認する。** 実マイクで録音の開始・停止と権限拒否を確認し、OS の録音許可とアプリのエラー表示が一致することを確かめる。配布候補では、モデルの導入からオフライン文字起こしまでの手順を通す。
