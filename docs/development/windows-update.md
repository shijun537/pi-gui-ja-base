# Windows アプリの更新

[計画02](windows-release-plan.md#pi-gui-02windows-アプリの更新)と[計画06](windows-release-plan.md#pi-gui-06独立配布と-lpヘルプの案内)で共有する公開版の方針と、非公開試験の範囲を記録する。

## 公開版の方針

- 独立リポジトリの GitHub Releases を初回配布と安定版の更新先の第一候補とする。計画06とリポジトリ、永続的なアプリ識別子、更新チャネルを確定し、配布設定とアプリの更新先に同じ値を使う。初回導入時に上流版が同居する場合は、インストール先と会話・設定の読み込み先を別々に検証する。
- Windows x64 のセットアップ版には `latest.yml` と同じビルドのセットアップを使う。検証済みの署名済みファイルとメタデータをそろえて公開する。ポータブル版は手動差し替えとし、配布リンクは公開準備が整った段階で LP と合わせて決める。
- 利用者がダウンロードと「再起動して適用」を個別に選ぶ。処理中の会話があれば適用を保留し、後から適用を選べるようにする。終了する前に、全ウィンドウで下書きの保存成功を確認し、会話の処理と永続化を完了させる。保存に失敗した場合はアプリを開いたまま再試行できるようにする。
- 更新はバージョン、対象アーキテクチャ、取得物の SHA-512、Windows が信頼するタイムスタンプ付き Authenticode 署名、インストール済みアプリに設定した発行元を確認してから適用する。発行元の設定が欠けている場合も拒否する。ダウンロード済みのファイルを再利用するときは、起動直前にも検証する。発行元を変更する場合は旧版から新しい発行元への移行を別途検証する。 [electron-builder の署名検証](https://www.electron.build/docs/features/security/) · [SignTool の署名検証](https://learn.microsoft.com/en-us/windows/win32/seccrypto/using-signtool-to-verify-a-file-signature)

## 署名の候補

| 方式                                   | 選定時に確認すること                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Azure Artifact Signing の Public Trust | 月額サービス。GitHub Actions から署名できる。発行者の種別と所在に利用条件があるため、個人または組織として登録できるかを最初に確認する。 [Microsoft の利用条件](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options)                                                                                                                                                                                                 |
| 認証局のコード署名証明書               | 発行者の名義、発行・更新費用、ハードウェアトークンまたはクラウドでの鍵保管、GitHub Actions から署名する方法を比較する。 [Microsoft の証明書比較](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options) · [DigiCert の署名例](https://docs.digicert.com/en/software-trust-manager/code-signing/sign-with-third-party-signing-tools/windows-applications/sign-authenticode-files-with-signtool-using-ksp-library.html) |
| SignPath Foundation                    | 条件を満たす OSS 向けに無料。既に同じ形態で配布されていることが条件で、署名の発行者名義は財団となる。初回公開後の候補。 [適用条件](https://signpath.org/terms)                                                                                                                                                                                                                                                                                         |

## 非公開試験

2026-11-25 に Windows x64（ビルド 26300）で、Electron 37.10.3 と `electron-updater` 6.8.12 を使い、試作用の未署名セットアップ版 1.0.1 と 1.0.2 を用意した。両版で配信メタデータとセットアップのサイズ・SHA-512 が一致した。試験用の配信先とモデルはループバックに限定し、通常版から独立したアプリ識別子、インストール先、Pi-GUI と Pi のデータ領域を使った。成果物と再実行用コードは作業フォルダの `scratchpad/windows-update-02` に保存した。

- 同じ版では更新が出ず、新版の検知だけではダウンロードが始まらないことを確認した。利用者による取消、通信切断、内容が一致しないファイル、発行元を設定した場合の未署名ファイルを確認した。いずれもそのまま適用できず、ダウンロードは再試行できた。正常なファイルのダウンロード後、通常終了して開き直したときも旧版だった。
- 合成モデルが応答中のときは適用を保留した。インストーラーをファイル置換前に停止させ、旧版を開き直すと、会話本文、適用直前の未送信下書き、テーマ設定が保持されていた。
- 初回の再試行ではインストール先の実行ファイルが 1.0.2 になった。起動時に試験用の環境変数を必要とする構成では、自動再起動後の起動を確認できなかった。再起動した試験版がインストール先から専用プロファイルを選べるようにした後、インストーラーから起動した新しいプロセスが 1.0.2 であることを確認した。
- 自動起動したプロセスとは別に、試験の制御下で同じインストール先の 1.0.2 と同じプロファイルを開き直した。新版の画面で会話本文、適用直前の未送信下書き、テーマ設定を照合できた。約74秒の通し試験が成功し、試験用のセットアップをアンインストールした。結果は `scratchpad/windows-update-02/result-e2e.json` に保存した。
- Windows の `pnpm check` と、フォルダ不要チャットを再起動後に開く既存の実 Electron テストが通った。

## 試作から製品実装へ引き継ぐ点

- 現行アプリの終了処理は、保存失敗やタイムアウト時も終了する。更新用の保存確認では、レンダラーからメインまで失敗を戻す。会話の実行中判定には送信開始から保存までと、後続メッセージ、承認待ちを含め、更新確定後の新規実行との競合も検証する。
- 更新の適用を記録し、再起動した版と照合して結果を判定する。インストーラーが起動した後の失敗も扱い、旧版を開ける場合は明示的に再試行できるようにする。ファイル置換中に中断した場合の復旧と、正しい発行元によるタイムスタンプ付き署名の受け入れは、製品と同じ構成のインストーラーで検証する。
