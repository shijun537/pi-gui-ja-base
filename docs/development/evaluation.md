# GUI 性能と Pi の推論品質の評価

対象のビルド、調べたい指標、条件を決めて単独で実行する。現行版の基準計測は1構成で始められる。比較する場合は、現行版と候補版を用意し、同じ Windows 機・合成データ・測定方法を使う。評価の成果は、測定値・実行条件・比較の制約を記録した結果。依存の採否や仕様の変更が必要な場合は、それぞれの作業で判断する。 [ループ設計の基準](workflows.md#ループ設計の基準)

変更の採否に必要な指標から測る。描画や起動に影響する変更では GUI、モデル・指示・ツール経路に影響する変更では Pi の比較を選ぶ。既存の基準値は、基準ビルドと計測条件が一致する場合に使い、候補だけを新たに測る。条件が変わった場合は必要な構成を測り直す。両方の指標が判断に関わる場合は両方を測る。

## GUI と Windows 配布物

開発環境をセットアップした後、リポジトリのルートからスクロール試験を実行する。Windows ではウィンドウを表示して、合成応答を流しながら計測する。結果は実行ごとに別の保存先を使う。 [開発環境のセットアップ](../../CONTRIBUTING.md#prerequisites)

```powershell
$env:PERF_SEED = '120'
$env:PERF_BODY = '2400'
$env:PERF_CPU = '0'
$perfOutput = Join-Path '.cache' ('perf-scroll-' + [guid]::NewGuid().ToString('N'))
.\tools\pnpm.cmd --filter @pi-gui/desktop run test:perf:scroll --output $perfOutput
```

- コマンド1回で3試行する。3回分の `PACED_WHEEL_RESULT` から、採取数の検査を通った試験のフレーム間隔と、ホイール入力からスクロールまでの95パーセンタイルを記録する。差が再現する場合は、必要に応じて描画やプロセス間通信の内訳を調べる。 [試験の実装](../../apps/desktop/tests/perf/streaming-profile.spec.ts#L411)
- 起動時間を評価する場合は、配布する実行ファイルの起動から入力が可能になるまでを測る。初回起動と再起動、開発ビルドのスクロール値をそれぞれ記録する。 [Windows 配布診断](../../.github/workflows/windows-release-diagnostic.yml)

## Pi の比較

1. **比較対象を決める。** Pi の版の影響を調べるときは GUI をそろえる。GUI や引き継ぎの影響を調べるときは Pi の版をそろえる。Pi CLI と比べる場合は同じ合成フォルダ、指示、ツールが使えるプロジェクトを使う。
2. **条件をそろえる。** 実際に選ばれたプロバイダ・モデル・推論レベル、履歴、システム指示、ツール、作業フォルダを確認する。各回は同じ初期データから始める。引き継ぎを評価する場合は、利用者が確定した下書きの条件が初回送信に届くことを確認する。意図した差異は結果に記録する。
3. **同じ課題を実行する。** 固定語の応答で送信経路を確認し、次に合成フォルダの `task.txt` に置いた文字列をツールで読み取って返させる。文字列の一致と、選択フォルダ内での読み取り確認を成功条件にする。同じ回数で比較し、成功数と試行数を記録する。実プロバイダの試験は明示の許可を受けた専用プロファイルで行う。 [既存の会話試験](../../apps/desktop/tests/live) · [実プロバイダの検証手順](../../.agents/skills/verify-pi-gui/SKILL.md)
4. **時間と利用量を記録する。** 送信から最初の応答が見えるまでと、本文の入出力・キャッシュトークンを記録する。測れる場合は送信準備、プロバイダ応答、画面表示に分ける。タイトル生成は別の呼び出しとして扱い、利用量を取得できない項目は「未計測」と書く。 [本文の利用量表示](../../apps/desktop/src/features/conversation/context-meter.tsx#L109)

## Jev の API キー運用

Jev を評価に採用する場合に適用する。Jev のクライアントと評価用ファイルは、開発者向けの独立した評価ツール内に置く。

1. **キーは評価プロセスだけに渡す。** ローカルでは起動した評価プロセスにだけ、CI では評価を実行するステップにだけ `TYPESAFE_API_KEY` を渡す。キーの値は秘密情報として管理する。配布ビルドは評価キーが設定されていない環境で実行する。
2. **実際の配布候補を調べる。** Windows のセットアップ版を検証用にインストールし、ポータブル版を展開する。両方の `app.asar`、`app.asar.unpacked`、その他の同梱リソースを確認し、Jev クライアント、評価用ファイル、キーが混入していないことを確かめる。混入防止の試験には実キーの代わりに固有のダミー値を使う。 [Windows 配布診断](../../.github/workflows/windows-release-diagnostic.yml)
3. **確認結果を配布記録に残す。** 対象の配布候補、確認した範囲、結果を記録する。混入が見つかった候補は配布を保留する。

## 結果の記録

評価記録に、対象差分・依存の版・Windows の版・実効モデル・課題と回数・測定値・未計測項目を残す。継続する案件では、進捗や参照元の PR からその記録を参照できるようにする。条件がそろわない場合は差を明記し、比較の判断は保留する。共有記録には合成データと計測結果を載せる。
